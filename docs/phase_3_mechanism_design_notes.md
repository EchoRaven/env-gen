# Phase 3 Mechanism — Design Notes (workflow `w23dyefwe`)

**Status:** Research notes. The Phase 3 inert scaffold
(`runtime/story_hub.py`) remains inert. The mechanism design below
was generated by an Ultracode workflow but failed adversarial
review with 1 BLOCKER. Capture the findings here so the next
implementer can pick up with full context.

**Workflow:** 14 agents, 4 candidate designs, judge picked Candidate C
("verification bundle"), 5-lens adversarial review found 1 blocker
+ 2 concerns + 2 nits. **Verdict: REJECT.**

---

## Chosen semantics (Candidate C — verification bundles)

A "story" is a NAMED VERIFICATION BUNDLE — a unique `story_id` mapped
to a frozen set of "probe target keys" that MUST ALL have a passing
evidence record before the bundle is considered delivered.

A probe-target key is a canonical string in one of a small closed
vocabulary of NAMESPACES:

| Namespace | Resolves against | Pass criteria |
|---|---|---|
| `api_smoke:<METHOD> <PATH>` | RunHub probe records | matching probe with status passed |
| `ui_flow:<flow_name>` | flow_coverage report | flow listed in `passed[]` |
| `table:<name>` | SchemaHub seed_audit | table registered + not in `flagged_tables` |
| `mcp:<server_name>` | RunHub mcp_probe records | matching probe with status passed |
| `visual:<route>` | gate_registry visual reviews | `metadata.route` matches + status==approved |
| `endpoint_contract:<endpoint_id>` | APIHub contract tests | latest test with passing verdict |

The gate `evaluate_story_gate()`:
- For each registered story, look up each target key in the right hub
- Mark each target pass / fail / missing
- Compute story_status: `delivered` iff every target passed; `failed`
  iff any target failed; else `evidence_pending`
- Return `{ok: bool, stories: [...]}` — `ok=True` iff every story
  status is `delivered`

Wired into `deliverability_check`: at phase >= 3.0, `evaluate_story_gate`
runs AFTER the six existing signal computations and APPENDS failures
to the shared `blockers` list. Strict AND semantics.

Actor gate: only `{orchestrator, product, planner}` may call
`register_story`; any other actor raises `PermissionError` at
phase >= 3.0. Mirrors the Phase 2.5 `record_probe` gate idiom.

## Adversarial review findings — BLOCKER

### B1. `_resolve_endpoint_contract` broken-by-construction

The resolver calls `apihub.get_contract_test_results(endpoint_id)`
(real signature at [apihub.py:508](../agent/env_generator/llm_generator/multi_agent/runtime/apihub.py)),
then does `latest = results[-1]` and reads `latest.get("verdict")`.

But contract-test records are written ONLY by `record_api_test`
([apihub.py:442-451](../agent/env_generator/llm_generator/multi_agent/runtime/apihub.py))
with shape `{id, endpoint_id, result, evidence, agent, created_at}` —
**there is no top-level `verdict` field.** `latest.get("verdict")`
will ALWAYS return `None`, so every consumed contract test is marked
"failed".

Additionally, `get_contract_test_results` iterates
`self._contract_tests.value().values()` with NO time sort, so
`results[-1]` is not "latest" in any reliable sense — it's just
last-inserted-key order.

The rationale promotes "lights up the currently-dormant APIHub
contract-test signal" as a free win. **It does not work against the
existing API.**

### Fix options

a) Inspect `latest.get("result", {})` for a verdict-like key the
   existing writers actually populate (audit `record_api_test`
   callsites first to see what they put in `result`).
b) Widen the audit: add an explicit `verdict` field to
   `record_api_test`'s record (additive change) + update
   `get_contract_test_results` to time-sort by `created_at` desc
   so "latest" is meaningful.
c) **Drop `endpoint_contract` from the v1 namespace vocabulary** and
   add it in a follow-up PR once `record_api_test` has been amended.

Recommend (c) for the initial Phase 3 PR — keeps scope tight.

## Adversarial review findings — CONCERNS

### C1. `_resolve_visual` uses wrong identity key

Visual review records (created by
`gate_registry.register_visual_review_task` at
[gate_registry.py:220-253](../agent/env_generator/llm_generator/multi_agent/runtime/gate_registry.py))
have NO `page_key` field — only `id` (from `_create_page` formatted
e.g. `page:visual_review:...`), `metadata.route`, `status`, `kind`.

The natural human-meaningful identity is `metadata.route`, not `id`.

### Fix

- Update namespace doc from `visual:<page_key>` to `visual:<route>`.
- Resolver reads `r.get("metadata", {}).get("route")` not `page_key`.

### C2. `register_story` actor gate divergence from canonical idiom

Four specific divergences from `schema_hub.register_table` /
`apihub.register_endpoint` / `RunHub.record_probe`:

1. Missing `.strip()` normalization. Canonical:
   `actor_id = (agent or provider or "").strip().lower()`.
2. Empty-actor fallthrough should be explicit:
   `if actor_id and actor_id not in allowed: raise`.
3. PermissionError message should embed `ELABORATION_REFACTOR_PHASE>={float}`
   + the actor + the allowed set, matching the existing format.
4. Provider/actor parameter sourcing should match
   `_get_phase() >= 3.0:` pattern.

### Fix

Copy the schema_hub.register_table gate body byte-for-byte and
substitute the allowed set + method name. Don't invent.

### C3. Overreach — design doesn't require anyone to call `register_story`

`evaluate_story_gate` with no registered stories returns `{ok: True}`
trivially. The design hard-gates *who* may register but has no
runtime mechanism that REQUIRES anyone to register. If the
orchestrator skips story registration, the gate is a no-op and the
mechanism contributes nothing.

### Fix options

a) At phase >= 3.0, `deliverability_check` requires AT LEAST ONE
   registered story or it fails with "story_registration_required".
b) Make story registration optional but configurable per project.
c) Leave as-is and document that story registration is a planner
   responsibility, not a runtime-enforced one.

Recommend (c) for v1 — keeps the change scope to "story_hub gates
the registered stories" without entangling with the broader question
"should every project have stories?".

## Adversarial review findings — NITS

- JsonStore mutation pattern: design uses
  `lambda m: {**m, story_id: record}` but the codebase convention is
  `lambda m: m.set(story_id, record, actor)`. Fix to mirror
  `RunHubStores` byte-for-byte.
- `_resolve_active_store()` / `_resolve_eventhub()` are referenced
  but never defined. Either add `hub_registry` kwarg to
  `register_story` (preferred) or document a
  `set_default_hub_registry()` injection point.

## Recommended next-PR scope

If/when Phase 3 mechanism is implemented, scope the FIRST PR to:

1. Implement namespaces: `api_smoke`, `ui_flow`, `table`, `mcp`
   (drop `visual` until C1 is fixed; drop `endpoint_contract` until
   B1 is fixed).
2. `register_story` actor gate byte-for-byte mirror of
   `schema_hub.register_table`.
3. `StoryHubStores` byte-for-byte mirror of `RunHubStores`.
4. `evaluate_story_gate` wired into `deliverability_check` at
   phase >= 3.0, AND-of-blockers semantics.
5. `ResolverFixtureContracts` test class that does NOT mock —
   constructs real fixture records via the canonical writing paths
   (`RunHub.start_run`, `seed_audit.audit_seed_data`,
   `flow_coverage.compute_flow_coverage`) and confirms each resolver
   returns `passed`. This would have caught the C1 + B1 schema
   misreads before the gate started silently rejecting valid
   evidence.

Followup PR(s):
- Add `visual` namespace with `metadata.route` indexing.
- Audit `record_api_test` callsites + add `verdict` field, then
  enable `endpoint_contract` namespace.
- Optional: phase>=3.0 require at least one registered story
  (C3 option-a) IF it surfaces in real pilots that stories are
  silently skipped.

## Why this wasn't shipped autonomously

The workflow's REJECT verdict was procedurally correct: 1 blocker
exists. The blocker is also substantively correct (verified by
adversarial review against the actual codebase — endpoint_contract
resolver IS broken-by-construction). Shipping a Phase 3 mechanism
that silently rejects valid contract-test evidence would be worse
than the inert scaffold.

The fixes are concrete (option (c) for B1: drop the namespace;
options for C1/C2/C3 above) but exceed autonomous-safe scope:
modifying `record_api_test` to add a verdict field would touch
existing callers, and the design decision between "require story
registration" (C3-a) vs "optional" (C3-c) is product judgment, not
mechanical implementation.

The next implementer should: (1) audit `record_api_test` callsites,
(2) decide on the verdict field shape, (3) implement the trimmed
v1 mechanism per the "next-PR scope" above with the
`ResolverFixtureContracts` test class as the primary correctness gate.
