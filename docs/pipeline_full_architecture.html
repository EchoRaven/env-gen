1. 总览：五大支柱与「由契约投影」的核心思想

整条流水线的入口是 Orchestrator.run(goal, requirements, resume, milestones)（orchestrator.py:661）。它是一个多智能体（multi-agent）系统，由一个常驻 orchestrator 加三条实现泳道（lane）——backend / frontend / verifier——协作，把一段自然语言描述 + 参考截图，变成一个真实可跑、可登录、有种子数据的完整 Web 应用。

它区别于「让 LLM 直接写整个应用」的关键，是五大支柱：

支柱作用代表机制
① 契约（Contract）endpoints / tables / ui_pages / verification_chains 是一等公民，存在 RegistryHub / SchemaHub / WorkHub 里，作为唯一事实源。register_endpoint / register_table / register_ui_page / register_verification_chain
② 由契约投影（Projection by construction）后端 main.py/handlers/models/DDL、前端 pages/routes/api.js —— 由框架确定性地从契约投影生成，而不是 LLM 手写后再校验。「一致性靠构造，而非事后校验」。render_skeleton_main / _generate_handler / project_missing_routes / scaffold_pages_from_contract
③ 材料准备（Material Prep）生成前先把参考截图拆成组件、测量真实颜色、预生成每屏 component spec，让前端「照着量出来的像素建」，而不是猜。4 块 Brick：extract_palette / decompose_reference / make_side_by_side / precompute_component_specs
④ 死锁不了的质量门（Bounded-deferral gates）交付前一系列门（功能门 + 视觉 + test-user）。每个门都是「不通过就 defer 重测；到达上限就 escape 大声交付」，永不死锁。_validate_delivery_gate / _visual_release_decision / squad_release_decision / browser_report_unusable
⑤ 交付时自愈（Heal Pipeline）交付前跑一组确定性、幂等的修复，收敛 lane 反复出现的缺陷（auth、打包、DDL 漂移、psycopg DSN、api.js 漂移……）。HealPipeline.repair_*

粗粒度阶段（写进 hub、监控可见）：init → implement → test → done（_enter_project_phase，orchestrator.py:515；底层是 WorkHub.set_project_phase，一个自由字符串字段，不是枚举）。
真正的流水线（每个里程碑内）：Kickoff（契约合成）→ Scaffold（DB/MCP/前端页脚手架）→ Implementation（泳道实现）→ Coordination/Validation 循环（每 tick 跑 api_smoke + 补救）→ Delivery（门全清后切 release）。这条推进不是离散状态翻转，而是由 hub 查询驱动：循环不断问 all_business_endpoints_implemented(...) 和 _validate_delivery_gate()，一旦返回「清」就交付。

3. Phase 0 · 材料准备（生成前）

这是你一直在完善的那部分：在任何 lane 醒来之前，把参考截图变成「可照着建的量化材料」。方法论文档在 /data/common/haibotong/outlook_components/PIPELINE.md，代码实现在 runtime/material_prep.py（Brick 1-3）+ runtime/reference_materials.py（Brick 4）+ tools/material_prep_tools.py（agent 工具封装）。

3.2 方法论（PIPELINE.md）：杠杆顺序 + 塌缩点

7 阶段核心循环：①收集参考 → ②裁成组件 → ③逐组件取色（别猜）→ ④写组件级 spec/prompt → ⑤建→截图→并排→改（循环）→ ⑥逐组件 2× 缩放像素对照 → ⑦多智能体对抗式复核。

杠杆顺序（最反直觉、最重要的结论）——相似度的驱动力按优先级排序：

大面积背景/材质 > 精确颜色 token > 信息密度 + 状态分布 > 图标风格 > 结构组件
大多数生成器把力气花在「结构」（最末位），所以「总是差一口气」。修法：按上面的顺序投入。例：Outlook 的 Mica 全屏壁纸 + 半透明面板占屏约 55%，用扁平占位背景一眼假；未读为主 → 蓝色为主，是暗色 Outlook 的视觉指纹。

5 类塌缩点（critic 必须专门盯）：①多/漏小元素；②语义色丢失（计数蓝、图标红/紫/金 → 全灰，最常见）；③状态数据不真实（全已读 vs 满屏未读蓝）；④密度/行高（生成器偏松）；⑤复合/分裂控件（New-mail 的分裂下拉）。社交 UI 另有一组（导航图标顺序、Follow/Following、转发/计数、故事条、全局 dock…）。

3.3 材料如何喂给前端 lane（3 条通道）

  1. Prompt 条目（prompts/v3/frontend_agent.j2:90）：指示 lane 先读 design/component_specs/<screen>.json（框架已在醒来前拆好：组件名 + region + role + state + 测量出的 background/accent hex），照着这些测量色逐组件建；截图后跑 zoom_compare(scale=2) 逐组件抓微偏差。
  2. 磁盘工件（工作区共同事实）：design/component_specs/*.json、design/reference_spec.json、design/references/、design/agent_notes.md。
  3. 运行时 agent 工具：上面 5 个工具，经 bundle 授予 frontend 泳道。

4. Phase 1 · Kickoff：契约合成

契约是 LLM 起草 → 确定性归一/兜底 → 才注册，任何字段进 store 前都被强制成一个「靠构造闭合」的规范形状。

合成管线（runtime/kickoff/run_kickoff.py）

  • try_synthesize()（:1460）轮询会议，返回 awaiting / conflict / validation_failed / ready；只有 ready 带 contract / task_tree / predicates。
  • _build_contract(drafts, description)（:583）是合成器：
    • 确定性兜底（FIX #42）：若 lane 什么都没起草，extract_contract_from_description() 用正则从结构化描述里抽 - METHOD /path 和 - table: col,col，契约永不为空。
    • UI 层自动补全：页面/组件 apis_used 里引用了但不在契约里的 endpoint 被追加（source=auto_from_ui_declaration）——靠构造闭合，而非拒绝。
    • 契约形状下限：每个 endpoint 补规范 response_key（/api/ → item/items 信封）+ 缺省 auth_required=True。
    • owner_scoped_reads 兜底：若 lane 没决定、且表有 owner 外键、且目标语义为「每用户私有」，则置 True（显式 lane 决定永远被尊重）。

注册（finalize_kickoff()，:1796，要求 status=="ready"）

按序 fail-fast 写 hub：每个 endpoint 经 normalize_to_registryhub_endpoint 后 register_endpoint(status="defined")；每个 table（把 owner_scoped_reads 提到 table_meta 以免被 normalize_table_schema 丢掉）register_table；每个 task create_task；持久化 predicates；close_meeting；publish_event("kickoff_complete")；记 phase=finalized。

「一致性靠构造」原则（kickoff/contract.py 模块 docstring）：kickoff 形状是生产者形状；RegistryHub 是系统事实源形状；唯一的转换是注册时的 normalize_to_registryhub_endpoint，永不反向——所以「契约漂移」这一类 bug 无法再进来。endpoint_id() 在 contract.py 与 registryhub.py 必须逐字节一致：都把 {param} 折叠成 {}（参数名无关）、都剥查询串，所以「一条路由 = 一个 id」。

5. Phase 2 · 实现与协同循环

5.1 协同 tick（orchestrator.py:1378-1611）

主循环每轮最多在 _project_delivered_event.wait() 上阻塞 60s；超时后每 tick 按序：

  1. 预算：重读 run_budget.json（UI 可实时调上限）；budget_exceeded 则跳出。
  2. stall nudge（coordination.py）：读 eventhub.get_all_agent_statuses()，一条 lane 只有在 ENVGEN_LANE_STALL_SEC=150 内发过心跳才算「活着」；持有 pending/in_progress 工作却沉默的 lane 收到紧急 task_ready；每个 stall 段最多 ENVGEN_MAX_SILENT_NUDGES=4 次。grace 120s、interval 60s。
  3. 确定性 api_smoke 验证：_maybe_run_framework_validation()（每 tick 跑，因为 LLM orchestrator 泳道常空转）。见 §8.1。
  4. fail-fast abort 检查：读 _fwval_abort_reason；有 abort-grace 缓冲。
  5. 确定性交付：_maybe_framework_deliver()（门全清则切 release）。见 §8。
  6. 协同 tick 派发：仅当 lane 空闲（orchestrator_task_done_event 已置，PROPOSAL #17 忙保护）且 _coordination_tick_due（done 置位 或 卡 ENVGEN_COORD_TICK_STUCK_SEC=300s）时，派一个 resident_coordination_tick LLM 任务（超时 180s）。连续 3 次空闲 tick 后 prompt 加升级附言。

5.2 泳道派发与补救

lane 不由 tick 直接派，而是由补救派发器派：_dispatch_unimplemented_routes / _dispatch_frontend_navigable / _dispatch_failing_checks / _dispatch_unwired_ui_pages / _dispatch_unbuilt_pages（委托 remediation_dispatcher.py）。哪个 check 失败 → 派给哪条 owner 泳道（见 §8.2 的 owner 表）。

5.3 卡死升级阶梯（framework_validation.py，键是失败 check 名的 frozenset）

_fwval_stuck_decision：wait → redispatch(≥2) → terminal(≥4) → abort(≥7)。常量：FWVAL_FAST_CAP=6、FWVAL_SLOW_INTERVAL_S=300、FWVAL_STUCK_REDISPATCH_AFTER=2、FWVAL_STUCK_TERMINAL_AFTER=4、FWVAL_STUCK_ABORT_AFTER=7。失败集合一变化，计数清零（有进展就不算卡）。

6. Phase 3 · 契约投影 By-Construction

6.1 后端投影

  • 主投影器 render_skeleton_main(endpoints, tables)（backend_skeleton.py:511）：先生成最终 main.py = 固定骨架 + auth 中间件 + custom-route include + 从契约投影出的全部业务 handler。静态路由排在参数路由前（/api/users/suggested 不被 /api/users/{id} 遮蔽）。
  • handler 生成 _generate_handler()（route_projector.py:534）：按 CRUD/nested 模式投影真正能跑的 FastAPI handler，绝不 404。CRUD 信封硬编码：集合 GET 返回 {"items":[...],"total":N}；单条/by-id//me/create/update/delete 返回 {"item":...}。POST 把 owner 外键绑到 user.id；失败给诚实 500，绝不假 201。
  • 读隔离（owner-scoping）by construction：表元数据 owner_scoped_reads → scoped_read_tables → 置位且 model 有 owner 外键且已认证时：by-id GET 对非属主加 404；集合 GET / search 过滤 owner_fk == user.id；nested 校验父资源属主。写（PUT/DELETE）永远 owner-gated，与读标志无关。两处投影点（render_skeleton_main + project_missing_routes）用同一个逐表决定。
  • 交付时补投 project_missing_routes(...)（route_projector.py:944）：给每个「已声明但无路由」的业务 endpoint 追加投影 handler（若主投影已出则 no-op）。
  • lane custom_routes 优先级 _custom_route_overrides_projected(method, path)（backend_skeleton.py:440）：对标准 CRUD 形状，写用投影版（丢弃 lane 的），但 lane 的 GET 胜出（return _is_get）——因为 lane 的 GET 带着域正确的读作用域，丢掉会漏（outlook run-9 跨用户泄漏）。动作动词/search/新形状 → custom 胜出。
  • models/DDL/seed：render_models() 投影 SQLAlchemy 模型；DDL 交付时从 ORM 反投影（repair_ddl_from_orm）以免与 handler 漂移；render_seed_data() 投影种子加载器，优先 lane 写的 seed_data.json，否则用内嵌 _SEED，按外键顺序填每张空表，含可登录 demo 用户（密码 "password"，盐 app_sandbox_salt_2024）。

6.2 前端脚手架（frontend_scaffold.py）

  • scaffold_pages_from_contract / _project_page_component：从注册的 ui_pages 投影真实数据页。
  • project_missing_ui_routes：additively 注入 lane 漏掉的已声明页路由（前端版的补投）。

6.3 验证链（verification chains）与「验证者驱动的隔离」

验证者驱动的读隔离（2026-06-30）：注册时，若某步是「跨用户拒绝探针」（expect 含 403/404、无 2xx、非纯 401），就把被探的集合段映到表名，若该表还没 owner_scoped_reads 就置 True。即：验证者断言「非属主必须被拒绝读 by-id」这一域判断本身，就把表标记为私有，后端 regen 于是由构造 owner-scope 其读——补上后端 agent 不可靠声明的漏洞（outlook run-9/10：scope 了 messages 忘了 events）。环境无关：公开资源没有隔离探针 → 永不 scope。

8. Phase 5 · 交付门详解（每个 gate 的逻辑）

交付发生在 _maybe_framework_deliver()（orchestrator.py:2139）。门按此序执行，全清才到 create_release：
api_smoke/RunHub（硬前提）→ 功能交付门 _validate_delivery_gate → PageBuild 门 → Visual 门 → Squad 门 → Browser 门 → 切 release。

五个门共享一个「有界延迟」范式：不通过就 defer（在 create_release 前 return、重派修复、下轮重测）；到达尝试上限或锚定首次 defer 的墙钟就 escape（大声交付）。所以任何门都不会死锁。

8.1 api_smoke / RunHub 门（GATE 0，硬前提）

文件：runtime/validation_runner.py（run_smoke_validation）+ framework_validation.py（maybe_run）+ tools/validation_tools.py（_record_runhub_run）。

  • 触发：每个空闲 tick，前提是契约已全实现（all_business_endpoints_implemented 或 _all_business_endpoints_have_route_code()）且尚无通过 run。
  • 如何起应用：docker compose down -v --remove-orphans 然后 up -d --build --remove-orphans——干净启动，无残留 pg 卷；用 fcntl 文件锁 .smoke_validation.lock（等 600s）串行化，防两次并发启动互相拆台。
  • 探针（全部须 status=="pass"）：frontend_navigable、docker_up、backend_port、backend_health（GET /health==200，90s 内）、auth_register_login（/auth/register 超集载荷铸 token 再 /auth/login）、business_endpoints_reachable（<500）、business_endpoints_implemented（已注册实现的路由非 404/405）、business_endpoints_correct_shape（item/items 信封）、business_writes_persist（POST 后 GET 回读含新 id）、auth_enforced_401、business_chain（跑验证链）、frontend_dead_controls、frontend_reachable。

  • 阻塞 or 咨询：阻塞。没有专门开关（它是核心裁决者）；create_release 在通过 run 记录前不可达。

8.2 功能交付门 _validate_delivery_gate（所有 check）

入口：validate_delivery_gate(...)（delivery_gate.py:828）。返回结构：{ok, state, soft_fail_only, failed_checks[], missing_files[], missing_dirs[], invalid_json[], business_chain, deliverability, validation_runtime, ...}。

软 vs 硬 的唯一规则（delivery_gate.py:1148-1153）：
state=="ok" ⟺ 零失败。
state=="waiting_for_retry"（软）⟺ 唯一失败恰好是 validation_retry_pending 且无 missing files/dirs/invalid JSON。
其他任何非空失败集 → state=="failed"（硬）。
即：validation_retry_pending 是唯一能产生软态的 check，且只有它单独出现时才软。

business_chain 门的两个细节

什么算「业务 endpoint」（lifecycle.is_business）：排除 kind∈{auth,oauth,infra,spine}、排除路径以 /auth/ /oauth/ /api/auth/ /api/oauth/ 开头或 ==/health、排除 is_control_surface_path（/api/v1/reset · init-tenant · admin · tenants…）。这张网只删不加——所以覆盖门永远不会开始要求一个控制面 endpoint（修 outlook M2 的 spine-endpoint 卡死）。

关于 run-12 的 api_coverage 卡死：因为 is_business 已经排除了 /api/auth/，所以那次卡死不是简单的框架 bug，而是验证者链创作方差（LLM 没把所有业务 endpoint 都写进链）。真正的解法是一个「覆盖由构造」的确定性兜底（未来的聚焦任务）。

链步如何匹配 endpoint（_uncovered_business_endpoints）：对每个业务 endpoint 建 endpoint_id(method,path)；对每个链步把 ${var} 重写成 {x} 再算 endpoint_id；endpoint_id 自身又把 {param} 折成 {}——所以链步 /api/posts/${id} 能匹配注册的 /api/posts/{post_id}。返回没被任何链步碰过的业务 endpoint 标签；出异常返回 []（降级为 no-op，绝不卡门）。
