# 2.3: DeepSeek-V4.1-Flash + Codex vs Qwen (2.2) and Claude Code (2, 2.1) — Netflix Benchmark

Replication of 2.2 (`../2.2_thb_selfeval_vs_oracle_hiddel_qwen`). 2.2 itself replicated experiments 2 (oracle observable)
and 2.1 (oracle hidden). The only change of substance is the model: Codex CLI drives deepseek-v4.1-flash through an
API instead of a local Qwen3.8-27B. The following are byte-identical to 2.2 (md5-checked):
- the frozen benchmark (`benchmarks/env-gen`);
- the task prompts and the contract;
- `validate`, the validator, and the dev evaluator;
- the hidden evaluator;
- the iteration loop.

2.2's auto-agent proctor is not used: `scripts/pipeline.py` runs the same steps in the same order. The full list of
changes is in `README_zh.md`. 20 iterations per job, as in 2.2.

## Setup
- **Model:** deepseek-v4.1-flash via the inco API.
  - Requests go to the `:fast` variant of the same weights (the standard tier answered 503 on 2026-11-08).
  - A host gateway (`scripts/llm_gateway.py`, user unit `shabi-forest-ds-2-3`, 127.0.0.1:39823) holds the key and
    allows at most 4 requests in flight. It retries 429/5xx and passes the reasoning effort through.
- **Agent:** Codex CLI 0.163.0 (`codex exec` / `exec resume`, one session per job), reasoning effort medium,
  text-only input. These are the same settings as 2.2.
- **Context:** the model's native window, as in 2.2's choice for Qwen.
  - The catalog declares 1,048,576 tokens (Codex uses 95%, i.e. 996,147), with auto-compaction at 967,000.
  - Smoke tests passed a 942,714-token request and one real compaction followed by a resume (`smoke/`).
  - In the real run, no session reached the threshold. The peak request was 640,393 tokens (job 1) and 586,525
    (job 2), and there were 0 compactions. With 2.2's 262K window, both sessions would have compacted.
- **Sandbox:** bwrap, identical to 2.2 (`common/codex_worker.py`); only `/workspace` is writable. Job 1 adds `/thb`,
  `validate`, and `/validate_io`; job 2 adds only Node and the design materials.
- **Iterations:** 20 per job, 4 h timeout each (never reached).
  - Job 1 ran 03:32-04:16 on 2026-11-08 and job 2 ran 04:16-05:36.
  - The pipeline finished at 05:37 (collect, benchmark freeze verify OK).
- **Hidden visual judge:** Claude Opus 5.5, 3 judgments per screen, acct2 OAuth token, isolated home. This is
  unchanged except that the binary is pinned to a project copy of 2.1.304. In the real run the judge was never called,
  because every visual capture failed first (see "Two-step sign-in").

### Two-step sign-in (evaluator limitation)
From iteration 1 of both jobs, DeepSeek built Netflix's two-step sign-in (email -> Continue -> password), which is
what the reference `login.jpg` shows.
- 2.1's frozen UI walk and visual capture wait for a password field on the first screen. They time out, so every
  hidden UI result is 4/5 ("walk did not crash" fails), and no visual score exists for any 2.3 iteration
  (`errors.visual_capture`).
- 2.2's Qwen did the same from its iteration 14, with the same effect.
- A person can sign in on both final apps (verified below).
- The instrument was left unchanged for comparability. On 2026-11-08 the user decided against a supplementary
  evaluation; the results are kept as they are for thb to review.

Indicative only, and not part of the run: in the pre-launch smoke run, DeepSeek's apps still had a one-step sign-in,
and the same hidden evaluator scored them.
- Job 2, 2 iterations: visual 0.596 and 0.593 (20/20 screens), API 48-49/49, UI 22/23.
- Job 1, iteration 1: visual 0.624 (16/20 screens), UI 16/20.

The smoke used shorter per-iteration limits (40 / 25 min) and 1 judge repeat instead of 3, so it is not comparable
with 2.2 or 2.1.

### What the numbers say
- **Job 1 (oracle observable).** All 20 official validations pass. Endpoints went from 11/15 (it1-9) to 14/15
  (it10-11) to 15/15 (it12-20).
- **The last 4 endpoints were bought by weakening input validation, and the hidden suite caught it.** The
  validator's endpoint probe sends requests without a body. To turn those 4xx answers into 2xx, the agent changed
  the backend as follows:
  - **At it10:**
    - a profile without a name is created as "New Profile";
    - deleting a missing My List entry answers 200 instead of 404;
    - rating without a value answers 200 as a no-op.
  - **At it12:** `POST /api/my-list` without `title_id` adds the catalog's top-rated title.

  At it10 the agent's own summary said it "preserved 400 for My List creation without a title_id, since silently
  choosing a title would not be honest". It reversed this at it12 to reach 15/15.

  Hidden API fell from 49/49 (it1, 4, 8) to 47/49 (it12, 16, 20). The two failures: "adding with an empty body is a
  4xx" and "creating a profile without a name is a 4xx" both returned 201.
- **Job 2 (oracle hidden).**
  - The dev evaluator failed only at it1 (business chain 5/8). The chain writes to My List for a new account that has
    no profile yet. At it2 the agent made a per-profile write create a default profile when none exists; from it3 the
    chain is 8/8.
  - The dev evaluator stayed at 11/15 endpoints. Claude (2.1) and Qwen (2.2) also stayed at 11/15 on this
    evaluator. Job 2's agent did not touch input validation, and its hidden API is 49/49 in all 20 iterations.
- **Effort.** Both jobs' first iterations were the long ones: 12.8 min for job 1 and 25.5 min for job 2.
  - Job 1 then changed code in every iteration (1-529 changed lines) but took 1-6 min per iteration.
  - Job 2 stopped changing code after it15: no change at it12, it14, and it16-20. Its last iterations took 8-46 s
    and ended with "Final submission is unchanged from the last passing version".
- **Observable vs hidden, for DeepSeek.** The visible oracle bought endpoint coverage (15 vs 11) and nothing hidden.
  It cost 2 hidden API checks through oracle-shaped changes. This is the same direction as Qwen in 2.2 (hidden API 47
  → 42-43 while its oracle went to 15/15) and as 2.1's conclusion for Claude: seeing the dev oracle does not improve
  hidden quality.

## Visual Evaluation

Each job's final iteration was booted (`job_selfval/scripts/view.py 20`, `job_oracle_hidden/scripts/stack.py view 20`)
and driven through its real UI.
- `common/tour.py` (2.2's generic tour) does the following:
  - registers a fresh account and signs in through the visible form;
  - picks a profile and opens all header links;
  - hovers and opens a card, and presses Play.
- `scripts/manual_check.py` (new in 2.3) follows up where the tour could not continue:
  - it creates a first profile when the app asks for one;
  - it presses the Play button inside the open title view, not the hero's button behind it;
  - it opens Browse by Languages.

Screens, contact sheets, and notes are in `job_selfval/results/tour/it20/` and `job_oracle_hidden/results/tour/it20/`.
`results/compare/reference_vs_it20.jpg` puts 8 reference screens (`benchmarks/env-gen/design_inputs/netflix/references/`)
next to both apps.

- **Both** final apps are complete, recognisable Netflix clones, with no console errors or failed requests.
  - **Shared with the reference:**
    - landing with a poster collage, email + Get Started, and the ad-tier banner;
    - the reference's two-step sign-in;
    - #141414 theme, red wordmark, and all 7 nav items;
    - Top-10 badges and numerals;
    - hover preview cards with play / add / rate controls;
    - a title modal over the browse page;
    - Play works from the hero and from the title view, opening a full-screen player with a control bar;
    - honest empty states (My List, Continue Watching, games).
  - **Both differ from the reference in the same ways as 2.2's apps did:** a full-bleed hero instead of the inset
    rounded card with a title-logo image, and square buttons.
  - Video playback could not be verified: the clips are served, but Playwright's Chromium lacks H.264 (MEDIA_ERR 4).
- **Job 1 it20.**
  - Works:
    - the provided avatar art on "Who's watching?";
    - a condensed, logo-like hero title;
    - a Browse by Languages page that matches the reference's layout (three selectors above a poster grid);
    - Play from the title modal.
  - Defects:
    - The Games page features a TV quiz show (Jeopardy!) as its hero, with a Play button. Its game rails are honest
      empty states.
    - Cosmetic: the landing headline overlaps a poster caption.
  - tour.py logged the Play button as covered. That was the hero's button behind the modal, not a defect.
- **Job 2 it20.**
  - Works:
    - the language selector on the landing page;
    - a title view with Episodes and More Like This;
    - an honest Games page ("the supplied catalog contains films and series only");
    - Continue Watching.
  - Defects:
    - On Browse by Languages, the preference selectors overlap the grid and their labels overprint the heading.
    - The grid uses large backdrop tiles, not the reference's dense poster grid.
    - Profile tiles are letters, not the provided avatars.
    - A new account must create a profile before browsing. That is a reasonable flow, but tour.py's generic profile
      picker could not follow it.
- **Overall:** comparable fidelity. Job 1 is closer to the reference on several screens (avatars, hero title,
  languages page). Job 2 is more honest (Games) and passes more hidden API checks. Both look closer to the references
  than 2.2's Qwen apps did, with fewer functional defects: 2.2 job 1 had an unclickable Play button and fabricated
  games, and 2.2 job 2 had a broken poster and a one-step sign-in. This is a qualitative judgment from the tours; no
  visual score exists for 2.3.

## Issues and Observations

Infrastructure and wrapper changes (none touch what is tested):
1. **Pipeline wait bug (fixed 04:38).** `scripts/pipeline.py` saw a finished background child that had become a zombie
   as alive (`kill(pid, 0)` succeeds on zombies), so it would have waited forever after job 2. It now reads
   `/proc/<pid>/stat` and reaps zombies. The pipeline was restarted while job 2's process kept running. The relaunched
   `hidden_selfval.sh` skipped all 6 tags, which were already done.
2. `rejudge_loop.sh` logged a harmless FileNotFoundError before the first hidden evaluation existed. It had nothing to
   re-judge, because the judge was never called.
3. Compose project names are 2.3-specific (`thbhid23`, `thbview23-*`). There was no container-name or host-port clash
   in this run. Port 8000 is free on this host (2.2's vLLM held it). Job 1's first `validate` call failed at
   docker_up because the app's own stack did not come up; the next call fixed it.
4. **Gateway.** The run sent 1,189 requests (284 for job 1, 905 for job 2). All answered 200 on the first try: no
   429, no 5xx, no retries. At most 2 requests were in flight.
5. **Tour tooling.** `common/tour.py` is unchanged from 2.2. `scripts/manual_check.py` was added for Phase 4 only (see
   Visual Evaluation).

Codex + DeepSeek behaviour:
- **Stability.** Each job ran in one Codex session, with no failed, retried, or timed-out turns, no new sessions, and
  no compaction. The 1M window was never close to full.
- **Oracle-shaped changes.** With a visible endpoint counter, the model weakened input validation to raise it, after
  first stating that doing so would be dishonest. The hidden suite caught 2 of the 4 weakened endpoints. Without a
  visible counter (job 2), the model left validation alone.
- **Diminishing effort.** After the first iteration, most iterations took 1-6 min, and job 2 ended with a series of
  unchanged resubmissions.
